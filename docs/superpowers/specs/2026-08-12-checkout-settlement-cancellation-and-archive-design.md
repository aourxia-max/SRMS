# 退租结算取消与工单归档设计

## 目标

避免“退租结算”页积累已处理工单，同时保留完整账务、合同与房态审计链路。

## 页面分区

退租结算工作区保持四个页签：

1. 发起退租：仅显示可发起退租的履行中合同。
2. 退租结算：仅显示仍需要在当前页处理的结算工单，包含 `DRAFT`、`PENDING`、`REJECTED`。
3. 押金退还确认：显示已确认结算且尚待处理退款或最终确认的工单。
4. 已退租合同：仅显示“结算已完成”且“合同已结束”的只读记录。

`APPROVED`、已登记退款、已退款或 `COMPLETED` 的工单不再出现在“退租结算”卡片区。已完成记录继续进入“已退租合同”。未完成但已进入退款环节的记录保留在“押金退还确认”页处理。

## 取消规则

“取消退租结算”适用于状态为 `DRAFT`、`PENDING`、`REJECTED` 的工单，`ADMIN` 与 `SUPER_ADMIN` 均可操作。取消不要求填写原因，但必须经过前端二次确认。

后端在单一数据库事务中执行：

- 将结算单状态更新为 `CANCELLED`；
- 将合同从 `PENDING_CHECKOUT` 恢复为 `ACTIVE`；
- 将房源从 `PENDING_CHECKOUT` 恢复为发起退租前的房态；
- 新增一条房态历史：来源为待退租，目标为恢复后的房态，业务类型为 `CHECKOUT`、业务 ID 为该结算单，系统原因固定为“取消退租结算”；
- 不删除结算单、结算项目、合同、账单、房态历史或任何财务流水。

恢复房态必须取同一结算单“发起退租”房态历史中的原始 `fromStatus`。若该历史缺失、合同或房源不再处于待退租，或状态已发生并发变化，整个操作拒绝并回滚，不猜测原房态。

`APPROVED`、已登记退款、已退款或 `COMPLETED` 的工单禁止取消，后端必须强制校验，不能依赖前端隐藏按钮。它们只会移出“退租结算”卡片区，不回滚已发生业务。

## 权限与接口

- 新增受 JWT 与角色守卫保护的 `POST /checkout-settlements/:id/cancel`。
- 后端仅允许 `ADMIN`、`SUPER_ADMIN` 调用，并返回现有统一响应结构。
- `GET /checkout-settlements` 默认仅返回 `DRAFT`、`PENDING`、`REJECTED`，防止已取消、已确认或已完成记录混入可编辑结算列表。
- 已取消工单不出现在默认四个页签；它仍保留在数据库和房态历史中，供后续审计查询。

## 交互与显示

- 草稿、待确认、已驳回工单卡片显示“取消退租结算”按钮；点击后显示中文二次确认，明确提示会恢复合同和房态。
- 取消成功后刷新列表，卡片立即从“退租结算”消失。
- 已确认、已退款、已完成工单在当前卡片区不显示“取消”或“删除”按钮。
- 已退租合同页保持只读，不提供编辑、删除、取消、重新结算、退款或审批入口。

## 数据与兼容性

- 使用既有 `CheckoutSettlementStatus.CANCELLED`，不新增枚举、表或 migration。
- 不回滚已发生的押金抵扣、退款流水、账单作废、合同结束或最终房态变更；这些情况均不允许取消。
- 不修改历史业务数据。

## 测试与验收

- 后端：草稿取消、待确认取消、已驳回取消、恢复原房态、事务回滚、缺失原房态历史拒绝、已确认/完成取消拒绝、并发状态变化拒绝、列表服务端过滤。
- 前端：仅草稿/待确认/已驳回显示取消按钮；二次确认；取消成功刷新；已确认或完成记录不出现在结算卡片区；已退租合同保持只读。
- 回归：现有发起、提交、确认、退款、零额完成及已退租合同流程保持不变。
