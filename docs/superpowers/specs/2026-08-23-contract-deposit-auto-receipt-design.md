# 合同押金自动入账与财务押金余额设计

日期：2026-08-23

## 需求变更性质

本设计是经用户确认的正式业务规则变更，覆盖 SRMS-RB-1.0 及现有文档中“合同押金仅表示应收押金、实际押金必须另行登记”的旧口径。

新口径为：新合同中填写的押金金额即代表该金额已经实际收到。合同正式创建时，系统必须同步形成真实、可审计的押金收款和押金流水，不能只把合同字段当作退租可退余额，也不能绕过财务流水直接参与结算。

本次变更不补记、不修改已有合同的数据。已有合同原本存在的真实押金流水继续有效，并参与财务统计。

## 目标

- 新合同填写押金 10,000 元并正式创建成功后，合同押金收款、押金流水和当前押金余额均为 10,000 元。
- 用户不需要额外填写押金收款日期、收款方式或收款凭证。
- 合同创建与押金入账保持原子性、幂等性和可审计性。
- 财务中心展示系统当前保管的“押金余额总额”。
- 退租结算继续以不可覆盖的押金流水为唯一余额依据。

## 业务口径

### 新合同

- 合同创建表单将现有押金字段展示为“押金（填写即视为已收）”。
- 押金必须大于或等于 0，保留两位小数。
- 押金大于 0 时，合同正式创建成功即视为该押金已经足额收到。
- 押金等于 0 时，不生成零金额收款或零金额押金流水。
- 合同草稿只保存输入内容，不产生任何财务记录。草稿正式提交并创建合同时，按新合同规则入账。

### 已有合同

- 功能上线前已经存在于 `contracts` 表的合同不补记押金、不修改合同字段，也不建立历史待确认清单。
- 已有合同如果原本已经存在押金流水，其最新押金余额继续有效。
- 已有合同仅填写了合同押金但没有押金流水时，押金余额仍为 0；本次变更不得据此自动创造历史现金收入。
- 新规则只作用于功能上线后新创建的合同，包括功能上线后由草稿正式提交所创建的合同。

## 合同创建与押金入账

合同服务在现有合同创建数据库事务内完成以下步骤：

1. 校验房源、承租人、租期、租金、押金和权限。
2. 创建合同并生成最终合同编号。
3. 生成合同全租期账单、合同成员、附件及其他现有数据。
4. 当押金大于 0 时，创建一笔 `DEPOSIT` 类别、`CONFIRMED` 状态的收款记录。
5. 以该收款为来源创建一笔 `RECEIPT` 类型押金流水，`amount` 和 `balance_after` 均等于合同押金。
6. 完成房态和审计记录等现有合同创建步骤。

上述步骤必须处于同一数据库事务中。任一步骤失败时整体回滚，不得出现“合同创建成功但押金未入账”或“押金已入账但合同创建失败”。

自动押金收款使用以下系统值：

- 收款日期：合同正式创建日期，按系统业务时区生成。
- 收款方式：新增内部枚举 `SYSTEM_AUTO`，前端统一显示为“系统自动入账”。
- 经办人：正式创建合同的当前登录用户。
- 备注：`合同押金自动确认到账`。
- 收据编号和押金流水编号：后端生成的唯一编号，不允许前端指定。

自动收款必须具备确定的来源标识或等价的数据库唯一约束。接口重试、并发请求或服务异常恢复不得为同一合同生成第二笔合同押金初始入账。不能只依赖前端按钮禁用保证幂等。

## 生效后调整限制

- 正式创建后的合同不允许通过普通合同编辑直接覆盖押金金额。
- 后续押金增加、抵扣、退款、作废或更正必须使用对应的受控财务流程，并写入新的押金流水和安全审计。
- 退租结算、押金退款和财务统计继续读取押金流水最新 `balance_after`，不得直接读取合同押金字段作为当前余额。

## 财务中心

财务中心概览新增金额指标“押金余额总额”，不是合同数量，也不是历史累计收取金额。

计算口径：

```text
押金余额总额 = 全部合同押金收取 - 押金抵扣 - 押金退款
```

实现时以每份存在押金流水的合同最新一笔 `balance_after` 汇总，避免把每一笔历史余额快照重复相加。范围包含所有仍有非零余额的合同，不按合同当前状态排除；正常结束的合同余额应已归零，异常非零余额仍应计入，以便财务发现问题。

- 金额格式为人民币，保留两位小数。
- 没有押金流水时显示 `¥0.00`。
- 沿用现有财务中心查看权限；前端控制展示的同时，后端接口必须强制校验权限。
- 财务概览接口返回独立字段 `depositBalanceTotal`，不得由前端拉取全部流水后自行求和。

## 数据结构与兼容

- 保留数据库列 `contracts.deposit_required` 和 API 字段 `depositRequired`，避免无必要的大范围字段迁移；文档语义改为“合同创建时确认已收的初始押金”。
- `PaymentMethod` 增加 `SYSTEM_AUTO`，并同步数据库枚举、Prisma 模型、前后端中文映射及导出显示。
- 自动押金收款仍使用现有 `payments` 和 `deposit_transactions`，不新增平行的押金余额表。
- 为自动初始入账增加后端可验证的唯一来源约束；migration 上线前必须检查现有数据，不能破坏已有手工押金收款。
- migration 只改变结构，不执行历史押金补账。

## 权限、安全与审计

- 继续沿用现有合同创建权限，只有后端授权通过的用户才能触发合同和押金自动入账。
- 经办人记录为创建合同的用户，自动入账来源、合同编号、收款编号和流水编号必须可追溯。
- 前端隐藏或禁用字段不能代替后端校验。
- 押金自动入账不得进入租金账单分配，不得增加租金实收金额。
- 财务现金流中的该笔记录显示为“押金收取”，收款方式显示“系统自动入账”。

## 错误处理

- 押金小于 0、格式非法或超出金额上限时拒绝创建合同，并返回中文提示。
- 押金收款或流水创建失败时，整个合同创建事务失败并返回中文提示。
- 唯一来源冲突时不得补写第二笔记录；后端应识别为重复请求或数据冲突并安全失败。
- 财务中心汇总失败时不得返回部分汇总结果，应返回统一错误响应并记录服务端错误日志，日志不得包含密码或密钥。

## 测试与验收

### 后端单元与服务测试

- 新合同押金 10,000 元时，合同、已确认押金收款和 `RECEIPT` 押金流水在同一事务内创建。
- 收款金额、流水金额和 `balance_after` 均为 10,000 元。
- 押金为 0 时不创建收款和流水。
- 保存草稿不创建收款和流水；草稿正式提交后按新合同规则创建。
- 合同创建任一步骤失败时，合同和押金数据全部回滚。
- 重复或并发请求不会重复生成合同初始押金。
- 已有合同不执行历史补账。
- 合同创建后普通编辑不能直接覆盖押金金额。
- 自动押金不分配到租金账单，不增加租金实收。
- 押金余额总额按各合同最新 `balance_after` 求和，而不是累加历史快照。
- 财务概览接口无权限时拒绝访问。

### 前端测试

- 合同表单显示“押金（填写即视为已收）”，不新增收款日期、收款方式或凭证字段。
- 合同创建成功后，合同详情和退租财务快照显示正确押金余额。
- 财务中心显示“押金余额总额”和人民币金额。
- `SYSTEM_AUTO` 在收款详情、财务流水和导出中均显示“系统自动入账”，不暴露英文枚举。

### 集成验收

1. 新建押金为 10,000 元的合同。
2. 核对合同创建成功，并且仅生成一笔押金收款和一笔押金流水。
3. 核对收款状态为“已确认”、方式为“系统自动入账”、押金余额为 10,000 元。
4. 发起该合同退租，核对财务快照和结算单的押金金额为 10,000 元。
5. 完成抵扣或退款后，核对合同押金余额和财务中心押金余额总额同步减少。
6. 核对一份上线前已有、仅填写合同押金但无流水的合同仍保持原状。

## 不在本次范围

- 不补记或清洗已有合同押金。
- 不新增历史押金待确认清单。
- 不要求用户填写押金收款日期、收款方式或押金凭证。
- 不把合同押金直接当作退租余额，仍以押金流水为唯一余额依据。
- 不改变租金、优惠、预收款、退款和退租结算的其他冻结规则。
- 不部署线上环境，除非用户后续明确要求。
